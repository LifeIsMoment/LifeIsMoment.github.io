테스트 커버리지 기준이 포화된 뒤에도 검사가 필요한 이유

LLM 생성 코드의 테스트 선택과 테스트 오라클의 한계를 구분하는 경험적 소프트웨어공학 연구 노트입니다.

소프트웨어 검증연구 해설 · 탐색적 원고2026.11.18약 5분

선택한 테스트가 기준 커버리지를 모두 달성했다고 해서 프로그램에 오류가 없다는 뜻은 아닙니다. 남은 테스트 예산을 어떻게 사용하는지에 따라 오류 발견의 순서가 달라질 수 있습니다.

1. 문제 정의

추가 커버리지를 제공하는 입력을 더 이상 찾지 못하는 시점에도, 아직 실행하지 않은 입력이 특정 오류를 드러낼 수 있습니다. 이를 테스트 선택 기준의 '포화'로 구분합니다.

2. 비교하는 정책

초기 core 테스트 선택을 고정한 뒤, 나머지 입력을 무작위·입력 다양성·reset-greedy·전체 커버리지 기준으로 배열하는 정책을 비교합니다. 정책 비교에서는 입력 풀과 생성 프로그램을 일정하게 유지하는 것이 중요합니다.

3. 테스트 오라클의 역할

선택 전략의 우수성을 평가하려면 먼저 '정답 출력'을 신뢰할 수 있어야 합니다. 제한된 감사 입력만으로 판정한 오류 여부가 전체 버그를 대표하지 않을 수 있다는 점을 실험 결과와 분리합니다.

4. 해석과 한계

첨부된 공동연구 원고의 현재 결과는 탐색적 기술 파일럿에 해당합니다. 독립적인 기대값 검토, 별도의 확인용 데이터, 준비·실행 비용 평가를 거쳐야 넓은 적용 가능성을 판단할 수 있습니다.
